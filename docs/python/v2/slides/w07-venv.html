两个现象，两个结论：都不要用全局环境制造事故

实验一 · uv pip compile同一顶层 numpy 的两个精确约束无解 
numpy==1.26.4
numpy==2.0.2

uv pip compile --python 3.12 conflict-requirements.txt

研究环境实测：退出码 1，requirements are unsatisfiable。compile 只解析并尝试输出锁定结果，不要求 venv，也不向全局 Python 安装；可能读取索引与缓存。

实验二 · 隔离临时环境API 差异是局部的、可观察的
探针1.26.42.0.2
np.float_→ float64已移除；建议 np.float64
np.mean([1,2,3])2.0仍为 2.0
np.dtype(np.float64)float64float64

以上为 Windows + uv 0.12.5 的实测结果；脚本捕获 AttributeError，两次正常退出。历史版本只用于复现差异，不是新作业推荐版本。

uv run --no-project --python 3.12 --with numpy==1.26.4 python numpy_probe.py
uv run --no-project --python 3.12 --with numpy==2.0.2 python numpy_probe.py

安全边界：--no-project + --with 使用隔离临时依赖环境，不改项目声明或全局 site-packages；UV 仍可能写用户级缓存、下载受管 Python / wheel。能维护代码就迁移到 np.float64；旧项目暂不能升级时，用独立环境明确保留约束并安排迁移。

统一模型：先问任务在哪一层，不先问“activate 什么”

70–73 分钟 · 机制过渡与四层定位
① 命令查找shell 输入 python / node / cargo / go 时，PATH、代理或 symlink 先找到哪个程序？
② 工具链选择Python 解释器、Node 运行时、Rust 编译工具链、Go 工具链分别由谁选择？UV / venv / conda、NVM、rustup、GOTOOLCHAIN 不可互相替换。
③ 依赖解析代码或模块从哪里解析？Python 看实际解释器的 sys.path 与 site-packages；Node 查找 node_modules；Cargo / Go 读取各自模块声明与锁定/校验信息。
④ 配置与缓存VIRTUAL_ENV、PYTHONPATH、UV / npm / Cargo / Go 模块缓存会影响什么？共享缓存不等于共享项目依赖版本。
Python 内也不是只有一种环境工具

UV：可发现/下载受管 Python，uv add 维护 pyproject 与 uv.lock，uv run 在项目环境执行。venv：用创建它的既有 Python，隔离第三方包，不负责下载任意 Python 版本。conda：可管理 Python 与其他软件包；激活还可能运行包脚本、设置原生库路径，比简化 venv 模型更复杂。

四条边界

① PATH 决定命令先找到谁；② 实际解释器决定模块解析上下文；③ VIRTUAL_ENV 与 (.venv) 提示符只是证据之一；④ 激活只影响当前 shell，conda 还可能执行包激活脚本。

# 仅观察已建环境：已 sync、依赖齐全、lock 与 pyproject 一致
uv run --no-sync --locked python -c "import sys, numpy;
print('executable=', sys.executable);
print('is_venv=', sys.prefix != sys.base_prefix);
print('prefix=', sys.prefix);
print('numpy=', numpy.__version__);
print('numpy_file=', numpy.__file__)"
研究环境实测摘录三类独立证据
  • executable= …\lab\.venv\Scripts\python.exe
  • is_venv= True
  • numpy_file= …\lab\.venv\Lib\site-packages\numpy\__init__.py
PATH ≠ sys.path；观察也不冒称只读

PYTHONPATH ≠ venv。普通 uv run --locked 可能同步项目环境并写缓存；这里只为观察已建环境，才用 --no-sync --locked，前提是已成功 uv sync --locked、依赖齐全且锁与声明一致。未满足前提时先修复，不用 no-sync 掩盖问题。

GoGOTOOLCHAIN 与 go.mod 的 go / toolchain 行；不是手工 activatego.mod 声明模块与依赖，go.sum 校验模块内容；go list -m allGOPATH / GOMODCACHE 共享只读模块缓存；GOROOT 是当前工具链位置。go env GOMOD GOTOOLCHAIN GOPATH GOMODCACHE GOROOT
Node 反例

lodash 已声明但 nvm use 后仍找不到：先核对项目目录与 lockfile，再 npm ci / npm ls；若从未声明，应先 npm install lodash。npm ci 会重建 node_modules，执行前必须审查目录。

Go 反例

把 GOPATH 改成项目目录并不会“完成依赖隔离”。项目版本由模块声明与选择算法决定；共享同一版本缓存是正常复用，go.sum 也不是另一份版本声明。

三个文件各自回答什么？

pyproject.toml：直接依赖与项目元数据；uv.lock：精确解析结果，由 UV 管理，不手改；.python-version：项目默认 Python 版本请求。

requirements.txt 的正确位置

可记录并帮助还原 Python 依赖，适合兼容或交换；但它不锁定解释器、操作系统和全部系统条件，不是万能环境，也不是本周锁文件的替代品。

sync 也不是“全局清理”

uv sync 默认精确同步项目环境，会移除未选定的额外包；范围是项目 .venv，不是系统 Python。环境不可当作跨机器部署包直接拷贝。
