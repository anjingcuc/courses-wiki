    Python项目结构与模块化

    L17 现场：审查一段 AI 生成的代码

    这是课堂用的真实案例。左边是学生让 AI「写个函数统计词频」得到的第一版，右边是审查重构后——你能先自己找出几处问题？

    ai_code_review.py — 左：AI 初稿 ✗ · 右：审查重构 ✓
    问题① 密钥硬编码： api_key="sk-abc123" → os.getenv("DEEPSEEK_KEY") 问题② 命名含糊： def process(d): → def count_words(text: str) -> dict 问题③ 无边界处理： text.split() 空串也照跑 → if not text: return {} 问题④ 全局变量： results 写在函数外 → 收进函数，返回值交付 问题⑤ 零测试： 无 → assert count_words("a a b")=={"a":2,"b":1}

    审查三步法：① 密钥与敏感信息有没有进代码？② 名字能不能自解释、函数是否只做一件事？ ③ 空输入 / 超长输入 / 非法类型会怎样？过完三问再运行验证。这套流程在 M6 项目冲刺里每天都要用。

    AI 时代为什么更需要虚拟环境

    核心论证——传统课程常把虚拟环境讲成可有可无的整洁习惯，在 AI 时代它已是必需：

    依赖冲突同一个顶层包不能同时是两个版本

    爬虫项目与可视化项目可能带不同依赖约束。同一 Python 环境的同一个顶层包不能同时解析成两个版本，升级也可能移除旧 API；独立 .venv 让两个项目各自声明、各自验证，而不是在全局环境反复升降级。

    AI 引入的版本漂移AI 推荐的版本各不相同

    每次问 AI 安装命令，它推荐的版本可能不一致。pyproject.toml 声明直接依赖，uv.lock 记录精确解析结果；Agent 的变更仍须审查并用实际运行验证。

    项目交付清单独立环境与复现自检

    可视化项目保留 pyproject.toml、.python-version 与 uv.lock，.venv 不提交；README 写明 uv sync --locked 和 uv run --locked，并记录实际运行证据。

    换机 / 协作依据声明与锁文件重建

    队友取得源码后执行 uv sync --locked，再运行项目验证；不要复制 .venv。requirements.txt 可用于兼容其他工具，但不锁定解释器、操作系统与全部系统条件。

    L18 目标结构：单文件脚本 → 模块化项目

    my_ai_app/ — 作业③的目标形态
    my_ai_app/ ├── .env # API Key（已加入 .gitignore，不进入版本库） ├── .gitignore ├── pyproject.toml # 项目元数据与直接依赖约束 ├── uv.lock # UV 管理的精确依赖解析结果 ├── .python-version # 项目默认 Python 版本请求 ├── README.md # 安装/运行/功能说明 └── app/ ├── __init__.py ├── config.py # 读环境变量、常量集中管理 ├── client.py # 大模型 API 封装（L19 的成果放这） ├── stats.py # 数据处理函数 └── main.py # 入口：python -m app.main
