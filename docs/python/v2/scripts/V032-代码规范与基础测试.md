### [0:30-2:00] 命名规范三原则

**【画面】** PPT 展示三行规则，逐条弹出：函数用动词、变量用名词、常量大写。每条配一个代码示例。最后展示"改名前 vs 改名后"的对比。

**【旁白】** 第一步——命名规范。三个原则，记住就行。

**原则一：函数用动词**。函数是"做一件事"，所以名字应该是动作。`get_data`——获取数据；`save_file`——保存文件；`filter_high_scores`——筛选高分记录。一看就知道这个函数干什么。

**原则二：变量用名词**。变量是"存一个东西"，所以名字应该是事物。`user_list`——用户列表；`score`——分数；`api_key`——接口密钥。

**原则三：常量用大写**。程序里固定不变的值，全大写加下划线。`MAX_RETRY = 3`——最大重试次数；`DEFAULT_TIMEOUT = 10`——默认超时秒数。大写就是在告诉读代码的人——"这个值不会变，别在里面赋值"。

来看对比：

```python
# 改名前（AI 风格）
def proc(d):
    r = []
    for i in d:
        if i["s"] > 50:
            r.append(i)
    return r

# 改名后（规范风格）
def filter_high_scores(items, threshold=50):
    result = []
    for item in items:
        score = item.get("score", 0)
        if score > threshold:
            result.append(item)
    return result
```

同一个功能，右边你一眼就能看懂。这就是命名的价值。

### [2:00-3:00] 函数拆分与注释

**【画面】** VS Code 中展示一个 40 行的函数，高亮标出行数。然后动画把它拆成两个函数——一个负责获取数据，一个负责筛选。右侧弹出注释对比：左边的注释"# 遍历列表"被删掉，右边的注释"# API 返回 score 为 null 时视为 0 分"被保留。

**【旁白】** 第二步——函数拆分和注释。

**函数拆分的原则是"单一职责"**——一个函数只做一件事。经验法则：**一个函数超过 20 行，就该考虑拆了**。比如上集那段代码，`processData` 函数既负责调 API 又负责筛选数据——拆成 `fetch_items` 和 `filter_high_scores` 两个函数，各管一件事。好处是什么？筛选逻辑可以单独测试，不用真的去调 API。

**注释的原则是"写为什么，不写做了什么"**。代码本身就能说明做了什么——`for item in items` 就是遍历列表，不用写注释 "# 遍历列表"。但有些决策代码看不出来，比如：

```python
# API 返回 score 为 null 时视为 0 分
score = item.get("score", 0)
```

为什么默认值是 0 而不是跳过？因为产品需求决定"没有分数的记录当作 0 分处理"。这种决策原因，必须写注释。**注释解释的是"为什么"，不是"是什么"**。

### [3:00-4:00] assert 基础测试语法

**【画面】** 终端中先演示最简单的 assert 语句。然后 VS Code 中展示一个函数和对应的 assert 测试代码，运行后输出无报错（通过）。

**【旁白】** 第三步——写测试。用最简单的工具：`assert`。

`assert` 的语法很简单——`assert 条件`。条件为 True，什么都不发生，静默通过。条件为 False，立刻抛出 `AssertionError`，程序停下来。

```python
assert 1 + 1 == 2    # 通过，什么都不输出
assert 1 + 1 == 3    # 失败，AssertionError
```

怎么用？给你的函数准备输入，调用它，然后 assert 验证输出。看这个函数：

```python
def filter_high_scores(items, threshold=50):
    result = []
    for item in items:
        score = item.get("score")
        if score is not None and score > threshold:
            result.append({"name": item["name"], "score": score})
    return result
```

写一条测试：

```python
items = [
    {"name": "Alice", "score": 80},
    {"name": "Bob", "score": 30},
]
result = filter_high_scores(items, threshold=50)
assert len(result) == 1
assert result[0]["name"] == "Alice"
```

准备输入数据，调用函数，断言结果——只有 Alice 的 80 分大于 50，所以返回列表长度应该是 1，第一条名字应该是 Alice。assert 通过，说明函数行为正确。

### [4:00-5:30] 可运行闭环：正常输入 + 边界输入

**【画面】** VS Code 中展示完整的 `test_filter_high_scores` 函数，包含正常输入和四种边界输入。终端运行，逐条 assert 通过，最后输出 `所有测试通过 ✅`。

**【旁白】** 正常输入测了还不够。真正保护你的，是**边界测试**。核心思维——**测试不是证明代码对，而是尽早发现代码错**。

来看完整的测试，一条正常输入加四条边界输入：

```python
def test_filter_high_scores():
    # 正常输入
    items = [
        {"name": "Alice", "score": 80},
        {"name": "Bob", "score": 30},
        {"name": "Charlie", "score": 60}
    ]
    result = filter_high_scores(items, threshold=50)
    assert len(result) == 2
    assert result[0]["name"] == "Alice"
    assert result[1]["name"] == "Charlie"

    # 边界1：空列表
    assert filter_high_scores([]) == []

    # 边界2：所有记录都不达标
    assert filter_high_scores([{"name": "X", "score": 10}]) == []

    # 边界3：score 恰好等于阈值（不包含）
    assert filter_high_scores([{"name": "X", "score": 50}], threshold=50) == []

    # 边界4：score 为 None
    items_none = [{"name": "Dave", "score": None}, {"name": "Eve", "score": 90}]
    result = filter_high_scores(items_none)
    assert len(result) == 1
    assert result[0]["name"] == "Eve"

    print("所有测试通过 ✅")
```

逐条看。**正常输入**——三个学生，两个达标，验证返回数量和名字。

**空列表**——API 返回 0 条数据时就是空列表。你的代码在空列表上崩了，用户就看到一个红色错误。

**全部不达标**——有数据但没有一条合格，应该返回空列表而不是 None 或报错。

**恰好等于阈值**——score 是 50，threshold 也是 50，50 不大于 50，不应该被选进来。这个边界最容易写错——如果把 `>` 写成了 `>=`，这条 assert 就会失败，帮你抓住 bug。

**score 为 None**——数据库里某些记录可能没有分数。函数用了 `is not None` 判断，None 值的记录会被安全跳过。

运行一下——所有测试通过。这五条 assert 就是你的安全网。以后改函数逻辑，跑一遍测试，通过就放心改，不通过就立刻知道改坏了哪里。

### [5:30-6:15] 测试思维总结

**【画面】** PPT 展示三句话："测试不是证明代码对，而是尽早发现代码错"、"正常输入 + 边界输入 = 基本覆盖"、"改完代码跑一遍测试 = 安全感"。

**【旁白】** 关于测试，记住三句话。

第一——**测试不是证明代码对，而是尽早发现代码错**。你没法穷举所有输入"证明"函数永远正确，但你可以覆盖关键边界，确保最常见的问题被抓住。

第二——**正常输入加边界输入等于基本覆盖**。正常输入保证基本功能没问题，边界输入防止极端场景崩溃。

第三——**改完代码跑一遍测试等于安全感**。以后你改了一行代码，不确定有没有影响别的功能——跑一遍 assert 测试，全绿就放心。这比"改完祈祷不出事"靠谱多了。

assert 是最简单的测试方式。工业界用 pytest、unittest 这些框架，功能更强但本质一样——都是"给输入，验证输出"。你现在用 assert 够了，核心是养成"写完函数就测一下"的习惯。

### 完整文件：test_demo.py

```python
# test_demo.py —— 命名规范 + assert 测试演示


def filter_high_scores(items, threshold=50):
    """从列表中筛选分数超过阈值的记录

    参数:
        items: 记录列表，每条记录有 name 和 score 字段
        threshold: 分数阈值，默认 50
    返回:
        list: 筛选后的记录列表
    """
    result = []
    for item in items:
        # API 返回 score 为 null 时跳过该记录
        score = item.get("score")
        if score is not None and score > threshold:
            result.append({"name": item["name"], "score": score})
    return result


# --- 测试 ---
def test_filter_high_scores():
    """filter_high_scores 的测试：正常输入 + 边界输入"""

    # 正常输入
    items = [
        {"name": "Alice", "score": 80},
        {"name": "Bob", "score": 30},
        {"name": "Charlie", "score": 60}
    ]
    result = filter_high_scores(items, threshold=50)
    assert len(result) == 2
    assert result[0]["name"] == "Alice"
    assert result[1]["name"] == "Charlie"

    # 边界1：空列表
    assert filter_high_scores([]) == []

    # 边界2：所有记录都不达标
    assert filter_high_scores([{"name": "X", "score": 10}]) == []

    # 边界3：score 恰好等于阈值（不包含）
    assert filter_high_scores([{"name": "X", "score": 50}], threshold=50) == []

    # 边界4：score 为 None
    items_none = [{"name": "Dave", "score": None}, {"name": "Eve", "score": 90}]
    result = filter_high_scores(items_none)
    assert len(result) == 1
    assert result[0]["name"] == "Eve"

    print("所有测试通过 ✅")


if __name__ == "__main__":
    test_filter_high_scores()
```
