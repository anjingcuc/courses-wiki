AI 生成代码的五类常见问题

①命名不一致——同一个变量一会儿叫 data、一会儿叫 result、一会儿叫 output
②超纲语法——用了你没学过的装饰器 / 元类 / 上下文管理器，看得懂才敢用
③边界缺失——没处理空列表、None、空字符串；一传边界值就崩
④异常处理粗暴——一个 except Exception 吞掉所有错误，bug 更难找
⑤过度工程化——简单需求上了三层抽象工厂；课程范围内坚持轻量方案

现场案例：审查一段「能跑但糟糕」的代码

# AI 初稿：功能是对的，问题你来找
api_key = "sk-abc123"                    # 问题①：密钥硬编码！
def process(d):                          # 问题②：process 是什么？d 是什么？
    return d.split()                    # 问题③：d 为空串/None 时崩
results = []                               # 问题④：全局变量，多函数共用
# ...零测试...                          # 问题⑤：没法验证对错
重构后：密钥进 os.getenv() · 函数改名 count_words(text: str) -> dict · 空输入返回 {} · 结果收进函数返回 · 补 assert count_words("a a b") == {"a":2,"b":1}

① 密钥与敏感信息

③ 边界

  • 过完三问再运行验证——这套流程在期末项目冲刺里每天都要用
  • 注释写「为什么」而不是「做了什么」——代码自己能说明做了什么

模块化：把巨石拆成积木

300 行的 main.py——你愿意接手维护吗？

  • 单文件三大问题：找代码难、改一处怕崩别处、没法复用
  • 拆分原则：按职责——一个文件一个主题
  • 厨房类比：储物间（配置）/ 切配（数据处理）/ 烹饪（API 调用）/ 摆盘（输出）
my_ai_app/
├── .env               # API Key（不进仓库）
├── .gitignore
├── requirements.txt
└── app/
    ├── config.py      # 读环境变量
    ├── client.py      # LLM 调用封装
    ├── stats.py       # 数据处理
    └── main.py        # 入口

配置与代码分离

# .env（已被 .gitignore 排除）
DEEPSEEK_KEY=sk-xxxxxxxx

# config.py —— 密钥进 .env，配置集中管理
import os
from dotenv import load_dotenv
load_dotenv()

API_KEY = os.getenv("DEEPSEEK_KEY")   # 读不到就是 None，不会泄露
MODEL = "deepseek-chat"
MAX_TOKENS = 2048
  • 原则：密钥进 .env，配置进 config.py，代码只读不存
  • 附赠好处：文件边界清晰的项目，AI 生成代码的质量也更高——好的结构让 AI 更好帮你
