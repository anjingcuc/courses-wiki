    [0:35-2:15] 维度一：技术深度——架构决定上限¶

    【画面】 PPT 标题"优秀项目剖析 A：技术深度"。先展示一个优秀项目的目录树：

    ai_customer_service/
├── api/            # FastAPI 路由层
├── ai_core/        # AI 核心逻辑（RAG / 对话管理）
├── data/           # 知识库文档
├── static/         # 前端静态资源
├── .env            # 环境变量
├── config.py       # 集中配置
└── main.py         # 入口

    用箭头标注"api/ 和 ai_core/ 分离"，旁边浮现注释："换模型只改 ai_core/，API 层不动"。然后展示 ai_core/rag.py 的核心代码片段（切分+检索+生成），高亮"重叠窗口切分"和"来源标注"两处。

    【旁白】 先看第一个维度——技术深度。这是全班答辩中技术最亮的一个项目：AI 客服机器人。

    第一眼看什么？项目结构。注意它的目录划分——api/ 放路由，ai_core/ 放 AI 逻辑，data/ 放知识库文档。这叫"关注点分离"。好处是什么？如果以后要把 DeepSeek 换成 Kimi，你只改 ai_core/，API 层一个字都不用动。很多组把所有代码堆在一个文件里——改一个功能，半个项目都要重测。

    再看它的 RAG 实现。亮点在文本切分——它不是按固定长度粗暴切断，而是用了"重叠窗口"，每段之间保留一段重复。为什么？避免一句话被切断后，上下文丢失。另一个亮点是检索结果带了来源标注——回答末尾注明"参考自售后文档第 3 条"。用户就知道，这个回答是有依据的，不是 AI 瞎编的。

    技术深度不是说用了多少个 API，而是——你的架构能不能支撑未来的扩展，你的 AI 核心逻辑是否经得起推敲。

    [2:15-3:55] 维度二：工程素养——细节决定下限¶

    【画面】 PPT 标题"优秀项目剖析 B：工程素养"。展示另一个优秀项目的几个亮点片段。片段一：函数定义 + docstring（def retrieve_relevant(query, top_k=3): """检索最相关的文档片段"""）。片段二：自定义异常类（class DocumentParseError(Exception): pass）和 API 层统一异常处理。片段三：.env.example 文件，每行都有注释说明。片段四：README 截图——有功能截图、安装步骤、技术栈表格。四个片段并排展示，字幕标注"命名 / 异常 / 配置 / 文档"。

    【旁白】 再看第二个维度——工程素养。这个项目功能跟上一个差不多，但它打动评委的是代码的"细节功夫"。

    看函数命名——load_and_split_documents、retrieve_relevant、generate_answer，一看名字就知道干什么。每个函数都有 docstring，没有超过 30 行的巨型函数。这不是炫技，是让队友能看懂、让自己三个月后还能维护。

    再看异常处理。大多数组的代码里只有一个 except Exception as e 打天下。这个组定义了自定义异常——DocumentParseError、RetrievalError，区分了文档解析失败、检索出错、API 超时等不同情况。用户看到的是友好提示，不是一堆堆栈跟踪。

    配置管理也很规范——所有可配置项集中在 config.py，.env.example 每一行都有注释。README 有功能截图、精确到每一条命令的安装步骤。

    记住这句话：AI 能帮你写代码，但 AI 不会自动帮你写好代码。工程素养，永远是人的责任。功能相同的情况下，工程素养决定了你的项目能走多远。

    [3:55-5:45] AI 生成代码的五个典型陷阱¶

    【画面】 PPT 展示"AI 生成代码的 5 个典型模式"，用 5 个卡片并排。每张卡片左边是"AI 生成的问题代码"，右边是"人工修正后的代码"。逐张翻出（或逐张高亮）：

    # 典型模式 问题 人工修正
    1 结构清晰但异常缺失 只写 except Exception 区分不同错误类型
    2 倾向过度设计 简单 CRUD 加了 Redis 缓存 判断"真的需要吗？"
    3 API Key 硬编码 api_key = "sk-xxx" 写在代码里 改为环境变量 os.environ
    4 前端配色不稳定 每次 AI 生成的颜色都不一样 定义 CSS 变量统一管理
    5 不理解业务上下文 AI 按通用模式写，不考虑你的实际场景 根据业务逻辑手动调整

    【旁白】 做完这个项目，你应该对 AI 生成代码的特点有了直觉。我总结了五个典型陷阱，下次审查 AI 代码时，重点看这几个地方。

    第一，异常处理缺失。AI 写的代码结构通常没问题，但 try/except 往往只有一个宽泛的 except Exception。你要补的是——区分网络超时、数据解析错误、用户输入非法这些不同情况。

    第二，过度设计。AI 有时候会"热心过头"——一个简单的增删改查，它给你加了一层 Redis 缓存、一个消息队列。你得判断：这个功能真的需要这些吗？不需要就删掉。

    第三，最常见的问题——API Key 硬编码。AI 不知道你的项目结构，经常把 Key 直接写在代码里。你必须改成环境变量，通过 os.environ 读取。答辩时好几个组因为这个被扣分。

    第四，前端配色不稳定。你让 AI 生成三次前端，它给你三种不同的配色方案。解决方法很简单——定义 CSS 变量，把颜色集中管理。

    第五，AI 不理解你的业务上下文。它按通用模式写代码，但你的项目有特定的业务逻辑。这部分必须人工调整。

    识别这些模式，不是让你排斥 AI——是让你更高效地审查 AI 代码。知道它容易在哪犯错，就知道该重点检查哪里。

    [5:45-7:15] 全班经验：六条可迁移的项目法则¶

    【画面】 PPT 展示"全班经验清单"，六条逐条浮现，每条配一个图标：

    1. 🔍 需求拆解比写代码更重要
    2. ✅ 先做 MVP 再迭代
    3. 🔧 前后端联调是最花时间的
    4. 🛡️ 异常处理是好项目和烂项目的分水岭
    5. 📝 Git commit 是后悔药
    6. 🤝 队友分工要早确定

    字幕在底部浮现："这些经验不只适用于 Python——它们是通用软件工程经验。"

    【旁白】 最后，全班同学一起总结了这 14 节课最重要的经验。我精选六条分享给你。

    第一条——需求拆解比写代码更重要。选题和模块划分做好，后面顺风顺水；没想清楚就开写，后面到处救火。L31 和 L32 花的时间，是整个项目里回报率最高的投资。

    第二条——先做 MVP 再迭代。先跑通核心功能，哪怕只有一个对话接口能返回结果。然后一点一点加功能。很多组想一口气做完所有功能，结果一个都没跑通。

    第三条——前后端联调是最花时间的。CORS 报错、数据格式不匹配、异步处理……这里坑最多。给联调预留足够的时间。

    第四条——异常处理是好项目和烂项目的分水岭。刚才那个工程素养最好的项目就是最好的例子。

    第五条——Git commit 是后悔药。大改之前先 commit，出了问题随时回退。好几组没 commit 就让 AI 大改，结果改坏了回不去。

    第六条——队友分工要早确定。谁做后端、谁做前端、谁做测试，第一天就商量好。

    这些经验不只适用于 Python 项目。以后你做任何软件项目，都会用到。

    [7:15-7:45] 小结¶

    【画面】 字幕条逐条出现："技术深度看架构 · 工程素养看细节 · AI 代码必须人工审查 · 经验比技术更可迁移"。最后弹出一句加粗的话："交付能力 > 技术数量"。

    【旁白】 总结一下。一个优秀的 AI 项目，三个维度缺一不可：技术深度决定上限，看的是架构设计和核心逻辑；工程素养决定下限，看的是命名、异常、配置和文档；AI 协作意识看的是——你能不能识别 AI 代码的陷阱并有效修正。记住：能稳定运行的交付，比功能多但 bug 也多的堆砌，有价值得多。

    展示物 3：RAG 核心代码片段（讲解"重叠窗口"和"来源标注"）¶

    # rag.py 核心片段 —— 展示技术深度的两个亮点

def split_with_overlap(text: str, chunk_size: int = 500, overlap: int = 100) -> list:
    """按段落切分，每段之间保留 overlap 个字符的重叠窗口

    重叠窗口避免一句话被切断后丢失上下文。
    """
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end])
        start = end - overlap  # 回退 overlap 个字符
    return chunks


def retrieve_and_answer(query: str, chunks: list, top_k: int = 3) -> str:
    """检索最相关的文档片段，生成带来源标注的回答"""
    # 检索 top_k 个最相关片段
    relevant = retrieve_relevant(query, chunks, top_k=top_k)

    # 在 prompt 中要求 AI 标注来源
    prompt = f"""基于以下文档片段回答问题。
在每个回答末尾，注明引用了哪个片段（片段已编号）。

文档片段：
{format_chunks(relevant)}

问题：{query}
"""
    answer = call_llm(prompt)
    return answer

    讲解要点： - 重叠窗口（overlap=100）避免语义被截断 - 来源标注让回答可追溯，降低幻觉风险

| 维度 | 普通项目 | 优秀项目 |

    展示物 5：AI 生成代码五个典型陷阱（幻灯片）¶

    ## AI 生成代码的 5 个典型陷阱

### 1. 异常处理缺失
- AI 写法：except Exception as e（一个打天下）
- 人工修正：区分超时 / 解析错误 / 输入非法

### 2. 倾向过度设计
- AI 写法：简单功能加了 Redis / 消息队列
- 人工修正：判断"真的需要吗？"，不需要就删

### 3. API Key 硬编码
- AI 写法：api_key = "sk-xxx" 写在源码中
- 人工修正：os.environ["API_KEY"] + .env 文件

### 4. 前端配色不稳定
- AI 写法：每次生成不同配色方案
- 人工修正：定义 CSS 变量，统一管理

### 5. 不理解业务上下文
- AI 写法：按通用模式写，不考虑实际场景
- 人工修正：根据业务逻辑手动调整

    展示物 6：全班经验清单（结尾用）¶

    ## 六条可迁移的项目法则

1. 需求拆解比写代码更重要（L31-L32 是回报率最高的投资）
2. 先做 MVP 再迭代（先跑通核心功能，再逐步加功能）
3. 前后端联调是最花时间的（CORS / 数据格式 / 异步，坑最多）
4. 异常处理是好项目和烂项目的分水岭
5. Git commit 是后悔药（大改前先 commit）
6. 队友分工要早确定（后端 / 前端 / 测试，第一天就分好）

> 这些经验不只适用于 Python —— 它们是通用的软件工程经验。

    录制注意¶

    1. 幻灯片信息密度要分层：本集是复盘类微课，没有代码实操，画面以 PPT 和代码截图为主。每张幻灯片不要堆太多文字——核心要点 3-5 条，用卡片或对比表格呈现。讲到每条时逐条高亮，避免观众面对一整屏文字失去焦点。
    2. 代码截图要配标注：展示优秀项目代码时，不要直接丢一段代码让观众自己看。用箭头、高亮、颜色标注关键设计点（如"重叠窗口""来源标注""自定义异常"），每段代码旁配一句话总结"好在哪"。讲解节奏是"展示→标注→讲亮点→总结可学习点"。
    3. "五个陷阱"用对比展示：AI 代码典型陷阱那段，一定要用左右对比——左边"AI 生成的问题代码"，右边"人工修正后的代码"。视觉对比比纯口述有效十倍。每张卡片停留 10-15 秒即可，不要拖。
    4. 语速和总字数：整体旁白约 1850 字，按 230 字/分钟控制在 8 分钟以内。五个陷阱和全班经验两部分信息密度最高，语速适当放慢；开场和结尾正常语速。保持"复盘"的语气——从容、有总结感，不是赶进度。
    5. 提问彩蛋段的 prompt 字幕条需在后期加上，确保观众能暂停照抄。
